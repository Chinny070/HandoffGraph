# Optional consumer contracts

The main HandoffGraph core stands alone. Consumers are separately deployed demonstrations; neither is required for contract eligibility.

1. `handoff_consumer_example.py`: binds to immutable graph address, workflow ID/root, stage ID and operator. `execute_once(receipt)` executes a protected action once only when the target stage is a final PASS, released, currently unquarantined, and historical Decision identity matches the submission/attempt. It checks the core through the single `is_release_bound` view (accepted state) AND a finalized-state gate: every validator fetches a `gen_call` with `status: finalized` from the StudioNet RPC under strict equality. Native `StorageType.LATEST_FINAL` reads hang on StudioNet, so they are not used.
2. `handoff_capability_consumer.py`: binds the same fields plus a 64-hex `action_hash`, expiry timestamp, immutable max uses (1–32), and nonce 1–32. `consume(nonce, requested_action, receipt)` requires correct operator, exact action, unused nonce, remaining usage and final-active graph proof. The action is demonstrated as an onchain capability consumption **event**, not a privileged call into an external EVM contract. Integration with an actual application requires that application's own authorization logic.

**Adversarial cases:** revoked upstream stage, paused workflow, mismatched root, mismatched stage, mismatched historical Decision, wrong receipt, early/non-final PASS, expired capability, wrong action, repeated nonce, wrong operator, usage cap, source unavailable. All must deny. Offline tests exist, and the behavior was exercised live on StudioNet (see `LIVE_PROOFS.md`). The finalized gate trusts the RPC endpoint: a dishonest endpoint can only deny, because the accepted-state gate is still required for any action.

**Integration sequence:** deploy core; create workflow and stage; seal, submit artifact, assess and finalize; release and verify `is_release_active` on latest-final state; deploy consumer pinned to actual workflow root; demonstrate pre-PASS or unreleased denial and final-PASS success; open counterexample and demonstrate **future** consumed actions deny; verify old already-consumed actions are not reversed. Never authorize a protected action from accepted-state alone; `execute_once` and `consume` require both gates. `can_execute` and `can_consume` are accepted-state advisory views only.
